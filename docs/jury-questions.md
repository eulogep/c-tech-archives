# Questions de jury — réponses courtes

Chaque réponse est conçue pour durer environ 20 à 45 secondes. Les formulations restent cohérentes avec le code livré et n’attribuent pas au MVP des mécanismes absents.

| Question | Réponse préparée |
|---|---|
| Pourquoi Django ? | Django fournit un cadre cohérent pour les modèles, formulaires, sessions, CSRF, administration et tests. Pour ce MVP server-rendered, il permet de garder les règles métier et de sécurité près des vues et de l’ORM, sans ajouter une architecture frontend séparée. |
| Pourquoi PostgreSQL ? | PostgreSQL convient à des données relationnelles avec contraintes, clés étrangères et transactions. Le projet utilise des référentiels, des archives, des utilisateurs et un audit ; cette structure se prête naturellement à une base relationnelle. |
| Pourquoi RBAC ? | Les utilisateurs n’ont pas tous le même périmètre documentaire. Le RBAC rend cette différence explicite : Consultant pour PUBLIC, Agent pour PUBLIC/INTERNAL et Administrateur pour tous les niveaux. La politique reste provisoire et à valider avec C-Tech. |
| Pourquoi 404 plutôt que 403 ? | Lorsqu’une archive est hors du périmètre visible, 404 évite de confirmer qu’elle existe. Pour une archive visible mais une action non autorisée, 403 reste approprié. Cette distinction réduit l’inférence d’informations confidentielles. |
| Pourquoi stockage privé ? | Une URL publique de fichier contournerait les contrôles applicatifs. Le document est donc conservé hors de `MEDIA_URL` et envoyé seulement par une vue Django qui vérifie l’utilisateur, le rôle et la confidentialité. |
| Pourquoi SHA-256 ? | SHA-256 fournit une empreinte déterministe du contenu. Au dépôt, le serveur enregistre une référence ; à la vérification, il compare le fichier courant à cette référence. `MISMATCH` signale une différence sans remplacer la valeur historique. |
| Pourquoi SHA-256 ne chiffre-t-il pas le document ? | SHA-256 est un hash à sens unique, pas un chiffrement réversible. Il permet de comparer une empreinte mais ne protège pas la confidentialité du contenu. Un chiffrement au repos demande une gestion de clés et une décision d’infrastructure hors périmètre MVP. |
| Pourquoi pas antivirus ? | Les validations de type, taille et signature réduisent les erreurs simples, mais ne remplacent pas un antivirus. Une analyse malware demande une solution, une politique de quarantaine, un traitement des faux positifs et une exploitation à valider avec C-Tech. |
| Pourquoi pas JWT ? | L’application est une interface Django server-rendered. Les sessions Django utilisent des cookies protégés et s’intègrent aux vues et au CSRF. JWT serait plus pertinent pour une API ou des clients séparés, qui ne font pas partie du MVP. |
| Pourquoi pas React ? | Les parcours sont documentaires et rendus côté serveur. Django Templates et CSS local réduisent la complexité, les dépendances et les risques d’incohérence entre frontend et règles serveur. L’interface reste responsive sans JavaScript applicatif obligatoire. |
| Pourquoi pas suppression physique ? | Une archive peut avoir une valeur historique, juridique ou opérationnelle. Sans règle de conservation validée, supprimer définitivement serait risqué. Le MVP propose création, lecture et modification des métadonnées, mais pas de route `delete`. |
| Pourquoi pas `fields="__all__"` ? | Une liste blanche de champs évite qu’un navigateur contrôle des champs techniques, par exemple `uploaded_by`, taille, checksum ou horodatages. Le serveur reste responsable de ces valeurs. |
| Comment empêchez-vous l’IDOR ? | Les listes, recherches, paginations, détails, téléchargements et vérifications partent d’un QuerySet déjà filtré par la visibilité du rôle. Une URL avec un identifiant connu ne récupère pas une archive hors périmètre. |
| Comment empêchez-vous l’injection SQL ? | Les vues utilisent l’ORM Django et des critères validés par formulaires. Le code ne construit pas de SQL en concaténant une saisie utilisateur. Les entrées SQL-like sont traitées comme texte de recherche. |
| Comment gérez-vous le XSS ? | Django échappe par défaut les valeurs rendues dans les templates. Les formulaires et messages sont rendus sans `safe` sur les données utilisateur. Des tests vérifient que des entrées contenant du HTML ou du script ne deviennent pas des balises actives. |
| Comment gérez-vous le CSRF ? | Les opérations qui modifient l’état sont des POST avec jeton CSRF : création, modification, déconnexion et vérification d’intégrité. Les recherches restent des GET, car elles ne modifient rien. |
| Que se passe-t-il si la base et le stockage sont compromis ? | SHA-256 ne suffit pas contre une modification simultanée du fichier et de sa référence en base. Il faudrait alors une signature numérique, une clé séparée, un stockage immuable ou une infrastructure de confiance distincte. C’est une limite documentée. |
| Le système est-il totalement sécurisé ? | Non. Le MVP applique des contrôles utiles et vérifiés, mais il n’a pas de MFA, rate limiting intégré, antivirus, SIEM/WORM, pentest externe ni certification OWASP. Une production exige une revue d’infrastructure et des décisions C-Tech. |
| Comment passeriez-vous en production ? | Il faudrait valider le domaine, HTTPS, proxy de confiance, secrets, PostgreSQL sauvegardé, cookies secure, HSTS, hôtes explicites, supervision, gestion de comptes et procédure incident. La configuration par environnement et `check --deploy` préparent ce travail sans le remplacer. |
| Django empêche-t-il toutes les attaques automatiquement ? | Non. Django fournit des protections utiles, comme CSRF et échappement par défaut, mais leur efficacité dépend aussi des décisions de vues, formulaires, QuerySets, stockage et configuration. Les tests transverses vérifient ces choix. |
| Une interface qui cache un bouton suffit-elle ? | Non. Cacher un bouton améliore l’expérience, mais un utilisateur peut appeler une URL ou fabriquer une requête. Les vues, QuerySets, mixins, formulaires et services appliquent donc toujours les règles côté serveur. |
| L’application est-elle certifiée OWASP ? | Non. T-014 est une revue de sécurité interne avec tests de régression. Elle ne constitue ni une certification OWASP ni un pentest externe. |
| Le projet est-il prêt production immédiatement ? | Non. Il est un MVP fonctionnel et documenté. Avant une production réelle, C-Tech doit valider les choix métier et l’infrastructure doit couvrir secrets, HTTPS, sauvegardes, antivirus, monitoring, incidents et contraintes de conformité. |
